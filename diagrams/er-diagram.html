VELOOP Rewards - Logical Data Model

Work Package H | Proposed design | prepared 28 Sep 2026, revised 10 Oct 2026
All entities and relationships below are PROPOSED. Only the Users entity's field list is confirmed to exist, and only in the SIMULATED sample file - every other entity, key and relationship requires verification with Engineering before it can be treated as a fact about the real VELOOP system.
PK = primary key    FK = foreign key    Relationship notation: ||--o{ = one-to-many (one Users row relates to zero-or-many child rows)    ||--|| = one-to-one

H1/H2 - Primary and foreign keys

  • users.user_id is the primary key referenced by every other entity as a foreign key. It is the backbone of the whole model.
  • tasks.task_id is referenced by task_activity.task_id.
  • task_activity.task_activity_id is referenced by rewards.task_activity_id (optional - not every reward comes from a task).
  • rewards.reward_id is referenced by wallet_transactions.reference_id when reference_type = 'reward'.
  • wallet_transactions.transaction_id is referenced by withdrawals.wallet_transaction_id and by itself (self-reference) via parent_transaction_id for reversals/corrections.
  • withdrawals.withdrawal_id stands alone as its own entity, linked back to Users and to its debit transaction in Wallet_Transactions.
  • referrals.referral_id links two Users rows: referring_user_id and referred_user_id (both foreign keys to the same users table).
  • feature_events.event_id stands alone (event-sourcing style); user_id and feature (to feature_registry) are its foreign keys.
  • feature_registry.feature_id is referenced by task definitions, rewards, and feature events wherever a "feature" property appears.

H3 - Relationship documentation

  • Users to Task_Activity: one-to-many. One user can attempt many tasks; every attempt belongs to exactly one user.
  • Tasks to Task_Activity: one-to-many. One task definition can be attempted many times, by many users.
  • Task_Activity to Rewards: one-to-one (optional). A validated task attempt produces at most one reward record; not every attempt results in a reward (e.g. failed attempts do not).
  • Users to Rewards: one-to-many. A user can receive many rewards over time.
  • Rewards to Wallet_Transactions: one-to-one (optional). A credited reward should correspond to exactly one wallet credit entry - this is the reconciliation check in Data Quality Control QC17.
  • Users to Wallet_Transactions: one-to-many. A user has many ledger entries over time.
  • Wallet_Transactions to Wallet_Transactions (self-reference): one-to-many. A reversal or correction entry points back to its parent transaction via parent_transaction_id.
  • Users to Withdrawals: one-to-many. A user can submit many withdrawal requests.
  • Withdrawals to Wallet_Transactions: one-to-one (optional). A completed withdrawal should link to exactly one debit entry (QC18).
  • Users to Referrals (as referrer): one-to-many, via referring_user_id.
  • Users to Referrals (as referred): one-to-one (optional), via referred_user_id - a user can only be "the referred user" once.
  • Users to Feature_Events: one-to-many. This is the general-purpose event stream; every tracked event in the Event Tracking Plan lands here, one row per event.
  • Feature_Registry to Feature_Events / Tasks / Rewards: one-to-many. The registry is a controlled lookup list; many events, tasks, and rewards reference the same feature.
  • Users to Support_Tickets: one-to-many (feature scope not yet confirmed - see Assumption A019).
